## 재현한 문제의 상세 근거

재현 테스트 이름은 아래에 접미사만 쓴다. 실제 이름은 모두 `TestAudit20260906`으로 시작한다. **검사 PASS는 올바른 동작이라는 뜻이 아니라, 해당 결함을 관찰했다는 뜻이다.**

### F01 — 요청한 청크와 다른 Content-Range를 수용

[download.go:1946](../client/download.go#L1946)의 `downloadChunkOnce`는 상태 206과 수신 바이트 수만 확인한다. 요청이 `bytes=3-5`인데 서버가 `bytes 0-2/6`과 `ABC`를 돌려주어도 위치 3에 기록한다. `abcDEF`가 `abcABC`로 바뀌고 nil error를 반환했다. `WrongChunkRange`로 재현했다.

쓰기 전에 unit/start/end/total을 엄격히 검증하고, 요청 범위와 불일치하면 데이터를 기록하지 않아야 한다. 재개 경로의 시작 위치 검증도 같은 파서로 통일할 필요가 있다.

### F02 — 청크 실패가 이미 완료된 이웃 영역을 손상

같은 [청크 쓰기 루프](../client/download.go#L1980)는 요청 길이로 읽기/쓰기를 제한하지 않는다. 이웃 청크가 `DEF`로 완료된 상태에서 0–2 요청에 `abcdef`가 도착하면 3–5도 덮어쓴다. 길이 오류 후 0–2 재시도가 `ABC`로 성공하면 최종 파일은 `ABCdef`다. 이웃 청크의 완료 표시는 그대로다. `OversizedChunkOverwritesNeighbor`는 이 유효한 작업 순서를 순차적으로 강제하여 재현한다. 실제 동시 다운로드에서는 완료 순서에 따라 드러나는 파일 데이터 경쟁이다.

청크 경계를 넘는 `WriteAt`을 금지하고 초과 데이터를 감지해야 한다. 예: 요청 길이 안에서만 쓰고 추가 1바이트는 오류 판정에만 사용한다. F01의 헤더 검사만으로는 거짓 헤더를 단 긴 body를 막을 수 없다.

### F03 — 재개 응답의 일부를 전체 완료로 취급

[downloadRangeOnce](../client/download.go#L1475)와 상위 재개 경로는 `bytes=3-` 요청에 `bytes 3-4/10`과 두 바이트만 도착해도 성공한다. 로컬 `abc`가 `abcde`가 되었는데 10바이트 중 5바이트로 완료했다. `ShortResumeAccepted`로 확인했다. 별도 FormatInfo.ContentLength가 있으면 이후 검사에서 잡힐 수 있지만, 미상인 source 포맷에서는 그대로 성공한다.

유효한 부분 응답을 이어 요청하거나 total까지 도달하지 않았음을 오류로 반환해야 한다. 응답의 end-start+1만 검사해서는 충분하지 않다.

### F04 — 실패한 part가 기존 최종 파일을 교체

[downloadURLToPathPart](../client/download.go#L1013)는 전송 직후 rename하고, [downloadStream](../client/download.go#L688)은 그 뒤 FormatInfo.ContentLength를 검사한다. 메타데이터 20바이트, 응답 3바이트를 주자 이전 정상 파일이 `bad`로 교체된 다음 TruncatedDownloadError가 반환됐다. `PartInstalledBeforeIntegrity`로 재현했다.

기대 크기/미디어 검증을 part 단계에서 완료한 뒤 최종 경로를 교체해야 한다. 실패 시 기존 출력과 재시도용 part를 보존해야 한다.

### F05 — source의 이중 캐시 키가 독립적으로 퇴출

[cacheSourceSession](../client/client.go#L382)은 ID 키와 input 키를 차례로 저장한다. 캐시 상한 1이면 ID 키가 곧바로 퇴출된다. [OpenStream](../client/stream_api.go#L18)은 input 키의 정보만 얻은 뒤 ID 키로 URL을 해석하므로 source를 YouTube로 오인하여 `invalid input: unsupported_input_shape`로 실패했다. `SourceCacheOne`으로 재현했다. 상한이 더 커도 다른 추출과 경쟁하여 두 키 중 하나만 남는 조건은 가능하다.

alias와 본체를 한 캐시 엔트리로 관리하거나, 진행 중인 작업에 source identity/headers를 직접 전달해야 한다. 단순히 최소 캐시 수를 2로 올리는 것은 경쟁 조건을 해결하지 못한다.

### F06 — 자막 sidecar API의 선택 옵션이 다운로드 단계에 전달되지 않음

[WriteRequestedSubtitleSidecars](../client/subtitle_sidecar.go#L62)의 IncludeManual/IncludeAuto는 `all`의 언어 목록을 만드는 데만 쓰이고, 실제 GetTranscript는 Client.Config.SubtitlePolicy를 따른다. public API에 `IncludeAuto=true`, `IncludeManual=false`, Languages=en을 주었는데 manual 자막이 기록됐다. `AutoSubtitleFlagIgnored`로 재현했다.

CLI는 Config의 PreferAutoGenerated도 설정하므로 이 재현과 동일하게 항상 manual을 선택한다고 볼 수는 없다. 그러나 해당 설정도 선호일 뿐 배제 조건이 아니며 public sidecar API의 옵션은 독립적으로 작동하지 않는다. 언어만 재선택하지 말고 선택한 구체적 caption track을 다운로드에 전달해야 한다.

### F07 — 빈 자막 선택 결과를 기본 언어 요청으로 오인

[subtitle_sidecar.go](../client/subtitle_sidecar.go#L79)에서 필터 결과가 비면 무조건 `en`을 넣는다. English만 있는 영상에 `all,-en`을 주어도 English를 저장했다. `ExcludedSubtitlesReappear`로 확인했다.

사용자가 언어를 지정하지 않은 경우와 명시적 필터 결과가 빈 경우를 구분해야 한다. 후자는 파일을 쓰지 않아야 한다.

### F08 — nil Transcript의 panic이 파일 생성 이후 발생

[WriteTranscript](../client/subtitle_output.go#L37)는 nil 검사를 하지 않는다. serializer가 먼저 os.Create로 기존 파일을 truncate한 다음 `transcript.Entries`에서 panic한다. `NilTranscriptDestroysFile`은 기존 `old` 파일이 0바이트로 바뀌는 것까지 확인했다.

파일을 열기 전에 입력을 검증하여 typed error를 반환하고, serializer도 임시 파일 후 교체 방식으로 통일하는 것이 좋다.

### F09 — 출력 디렉터리와 stdout 표식의 충돌

[EffectiveOutputTemplate](../client/download_options.go#L21)은 `OutputTemplate="-"`도 상대 파일명으로 보고 OutputPathDir에 붙인다. `PathDirBreaksStdout`은 출력이 `.../−`에 해당하는 일반 경로로 바뀌는 것을 확인한다. 실제 표식 문자는 ASCII `-`다.

`-P out -o -`에서 디렉터리 결합보다 stdout 판정을 먼저 해야 한다.

### F10 — Windows 예약 이름 판정이 마지막 점 기준

[isWindowsReservedName](../client/download.go#L2097)이 마지막 점 앞 문자열을 검사하여 `CON.foo.bar`를 `CON.foo`로 비교한다. `ReservedMultiDot`에서 위험한 토큰이 그대로 남았다. 기본 이름 정책의 목적과 어긋나며 Windows에서 생성 실패나 장치 이름 해석을 유발할 수 있다.

첫 번째 점 앞 기본 이름을 기준으로 판정하고 Windows의 추가 장치 이름 변형도 테스트해야 한다.

### F11 — 손상 archive 라인의 길이 예외

[OpenDownloadArchive](../client/download_archive.go#L25)는 손상 라인 무시를 문서화했지만 Scanner의 기본 토큰 한도를 넘는 라인은 전체 Open을 실패시킨다. 65,537자 손상 줄 뒤에 유효 ID를 넣자 `bufio.Scanner: token too long`으로 실패했다. `ArchiveLongCorruptLine`으로 재현했다.

줄 단위 길이 초과를 다음 개행까지 버리고 진행하도록 처리해야 한다. Scanner 한도를 크게 올리기만 하면 임계값만 이동한다.

### F12 — 마지막 항목의 context 취소 의미가 유실

[RunPlaylistItems](../client/playlist_run.go#L42)는 루프 진입 전 ctx.Err만 확인한다. 마지막 processor가 context.Canceled를 반환하면 일반 실패로 집계되고 `Aborted=false`, `AbortErr=nil`이 된다. `FinalItemCancellationLost`로 확인했다. CLI에서도 cancellation 대신 일반 playlist 실패로 바뀔 수 있다.

processor 반환 직후 context.Canceled/DeadlineExceeded와 ctx.Err를 판별해 AbortErr 및 skipped 수를 일관되게 설정해야 한다.

### F13 — stdout 결과의 바이트 수를 파일 stat로 계산

[downloadSingle](../client/download.go#L478)은 stdout 전송 후에도 `getFileSize("-")`를 사용한다. 미디어 5바이트를 정상 출력했지만 DownloadResult.Bytes는 0이었다. `StdoutByteCount`로 재현했다. 현재 디렉터리에 실제 `-` 파일이 있으면 그 크기를 잘못 보고할 수도 있다.

전송 writer의 바이트 수를 결과까지 전달해야 한다. MP3와 HLS pair에는 이미 countingWriter를 사용하는 별도 경로가 있어 동작이 불일치한다.

### F14 — manifest redirect의 최종 URL 소실

[HLS fetchManifest](../internal/downloader/hls.go#L205)는 body만 반환하고, 상대 주소를 원래 PlaylistURL에 붙인다. `/start → /dir/list.m3u8`, 본문 `seg.ts`에서 `/dir/seg.ts` 대신 `/seg.ts`를 요청하여 404가 났다. `RedirectBase`로 확인했다. DASH 및 format 추출의 manifest fetch에도 최종 응답 URL을 주소 기준으로 전달하는 구조가 없다.

fetch 결과에 `resp.Request.URL`을 포함하고, media/key/init/BaseURL 해석에 최종 URL을 사용해야 한다.

### F15 — HLS reader와 downloader의 fragment skip 정책 불일치

[HLSMediaSegmentReader.Next](../internal/downloader/hls_segments.go#L60)는 fetchSegmentBody 오류를 즉시 반환한다. SkipUnavailableFragments=true와 상한 1을 설정해도 첫 live segment 404에서 중단했다. `SegmentReaderIgnoresSkip`로 확인했다. 이 reader를 사용하는 분리 HLS OpenStream/stdout 병합이 영향을 받는다.

누락 판정, skip 누적, 상한, sequence 갱신을 일반 HLS downloader와 공유해야 한다.

### F16 — post-live의 skip 상한 미적용

[LiveAdaptiveDownloader.downloadFragment](../internal/downloader/liveadaptive.go#L94)는 404/410을 무조건 nil로 바꾸고 MaxSkippedFragments를 검사하지 않는다. 상한 1로 네 fragment를 모두 404 처리해도 0바이트 성공을 반환했다. `AdaptiveSkipLimit`으로 재현했다.

skip 누적 및 상한을 적용하고, 최소한 모든 fragment를 잃은 결과는 정상 다운로드로 기록하지 않아야 한다.

### F17 — dynamic DASH의 가용 구간 미반영

[extractSegments](../internal/downloader/dash_addressing.go#L15)는 availabilityStartTime으로 끝을 구하지만 `timeShiftBufferDepth`를 파싱하지 않고 startNumber부터 전부 생성한다. 1시간 지난 방송, 2초 fragment, 보존 30초 입력에서 1번부터 1,800개를 생성했다. `DASHLiveWindow`로 재현했다.

CDN에서 제거한 과거 fragment를 요청하여 실패하거나 대량 skip이 발생할 수 있다. 가용 시작 경계와 live-edge 정책을 계산하고 그 구간만 생성해야 한다. 현재 100,000개 제한은 무한 확장을 막지만 정상 장시간 방송도 끊을 수 있다.

### F18 — DASH SegmentList를 다른 addressing 방식으로 오인

[DASH 모델과 추출](../internal/downloader/dash.go#L50)은 SegmentList를 저장하지 않는다. Representation에 `BaseURL=media/`와 SegmentList(init, seg)를 주면 에러 없이 `media/` 하나만 반환했다. `DASHSegmentListIgnored`로 확인했다. formats 계층도 SegmentTemplate 유무만 확인하므로 이 표현을 direct HTTPS로 노출할 수 있다.

SegmentList를 구현하거나 적어도 명시적으로 unsupported로 거부해야 한다. SegmentBase의 indexRange 처리도 현재 별도 구현이 없어 지원 계약을 명확히 해야 한다.

### F19 — DASH DRM 표시 누락

[ParseDASHManifest](../internal/formats/dash.go#L94)는 ContentProtection을 파싱하지 않는다. `value="cenc"`가 선언된 representation이 IsDRM=false로 나온다. `DASHDRMUnmarked`로 확인했다. public selector의 IsDRM 필터가 작동하지 않아 암호화된 미디어가 정상 후보가 된다.

AdaptationSet/Representation의 보호 정보를 상속하여 IsDRM을 표시하고 제외 또는 명확한 오류를 반환해야 한다. DRM 해제를 구현하라는 제안이 아니다.

### F20 — 구체적 출력 경로가 두 번 렌더링

CLI의 [buildDownloadOptionsForVideo](../cmd/ytv1/adapters.go#L92)는 PredictOutputFilename 결과를 OutputPath에 넣지만, [downloadSingle](../client/download.go#L423)은 이를 다시 template로 처리한다. 제목 `literal %(id)s`에서 예측 `literal %(id)s.mp4`, 실제 `literal stub_42.mp4`가 되었다. `FilenameRenderedTwice`로 재현했다.

NoOverwrites의 검사 대상과 sidecar/media 이름도 달라질 수 있다. template와 최종 경로를 구분하거나 한 단계에서만 렌더링해야 한다. ApplyPlaylistTemplateContext에도 순차 ReplaceAll이 남아 있어 playlist 값 안의 token을 다시 해석할 여지가 있다.

### F21 — 명시적 format과 MP3 후처리 결합 누락

[BuildDownloadOptions](../client/download_options.go#L59)는 raw format이 빈 값 또는 best인 경우에만 ExtractAudio/AudioFormat을 mode로 변환한다. `-f 140 -x --audio-format mp3`는 Itag=140, Mode=best가 되어 MP3 경로를 타지 않는다. `ExtractMP3WithExplicitFormat`으로 확인했다.

입력 포맷 선택과 출력 변환을 독립적인 옵션으로 처리해야 한다. MP3 모드를 유지하면서 Itag 또는 FormatSelector를 지정하는 조합을 검증해야 한다.

### F22 — AV+audio 병합의 preview와 실행이 다름

[IsMergedSelection](../client/output_filename.go#L142)은 video-only+audio-only만 병합으로 본다. 기본 selector는 AV+bestaudio도 반환할 수 있고 downloadAndMerge는 이를 실제로 병합한다. `MergedPreviewAVPlusAudio`로 판정 차이를 확인했다. MergedItags도 첫 AV 포맷의 audio를 선택하여 별도 audio itag 대신 같은 itag를 반환할 수 있다.

예측 확장자·format id·후처리 판단과 실행의 track 분리를 하나의 함수에서 계산해야 한다. `HasVideo`인 포맷과 별도 `HasAudio && !HasVideo`인 포맷을 식별하는 식으로 계약을 맞출 수 있다.

### F23 — append 보존은 해결됐지만 archive 공유 상태는 stale

[DownloadArchive.Has](../client/download_archive.go#L77)는 Open 당시 ids map만 본다. 핸들 A가 Add+Sync를 마친 뒤에도 먼저 열어 둔 핸들 B의 Has는 false였다. `ConcurrentArchiveVisibility`로 확인했다. 다른 실행이 추가한 행을 덮어쓰는 이전 문제와는 별개로, 중복 다운로드·break-on-existing 누락이 남는다.

같은 프로세스에서는 path별 공유 상태/락을, 프로세스 간에는 변경분 재로딩과 적절한 파일 잠금을 검토해야 한다. archive의 Has/Add만으로 다운로드 자체를 원자적으로 선점할 수 없다는 범위도 문서화해야 한다.

### F24 — SOOP agent 오류가 미디어의 정상 종료로 위장

[agentHandler](../internal/source/soop/agentserve.go#L78)는 streamAgentMedia를 시작하기 전에 HTTP 200을 보내고, 오류를 stderr에만 쓴다. 연결 불가능한 로컬 agent를 지정했는데 응답은 200, body는 빈 값, 읽기는 정상 EOF였다. `AgentFailureLooksSuccessful`로 재현했다.

파일 downloader는 이 응답을 빈 성공으로 취급할 수 있고, 중간 실패는 잘린 정상 종료처럼 보인다. 첫 데이터 전 실패는 non-2xx로 반환하고, 헤더를 보낸 뒤 실패는 정상 EOF와 구별되도록 연결을 중단하거나 명시적 종료 상태를 전달해야 한다.

### F25 — 라이브 녹화 중단 시 모든 중간 데이터 삭제

[downloadAndMerge](../client/download.go#L550)의 두 downloader는 동시에 시작하지만 context 취소는 실패 경로로 끝나고, 기본 cleanup이 두 `.part`와 중간 파일을 삭제한다. 두 트랙에 실제 쓰기가 발생한 progress event를 기다린 뒤 취소하자 muxer는 호출되지 않고 디렉터리가 비었다. `LiveMergeCancelDeletesRecording`으로 재현했다.

녹화의 정상 stop과 실패 cancel을 구분하고, stop 시 bounded finalize를 수행하거나 최소한 녹화 데이터를 보존해야 한다. 두 트랙을 동시에 받는 이전 수정만으로 파일 녹화 수명 계약이 완성되지는 않았다.

### F26 — n 변환 실패가 nil error로 처리

[DecipherN](../internal/playerjs/decipher.go#L52)에서 정적 함수 추출은 성공했지만 결과가 부적합하고, runtime도 원본 n을 반환하면 두 유효성 검사가 모두 실패한다. 이때 err와 runtimeErr가 모두 nil이므로 마지막 return이 `"", nil`이 된다. 합성 JavaScript를 실제 goja 경로로 실행한 `InvalidNReturnsNilError`로 확인했다.

상위 cache/solver가 변환 성공으로 기록하고 URL의 n을 빈 값으로 바꿀 수 있다. 유효성 검사를 통과하지 못한 결과에는 반드시 명시적 오류를 반환해야 한다. 예: `return "", errors.New("invalid n decipher output")`.

### F34 — custom DefaultTransport에서 프록시 설정 우회

[defaultHTTPClient](../client/http_client.go#L41)는 http.DefaultTransport가 *http.Transport가 아니면 즉시 반환한다. Config.HTTPClient가 nil인 상황에서도 ProxyURL 검증·적용, SourceAddress, TLS 설정을 생략한다. custom RoundTripper와 잘못된 proxy를 설정한 재현에서 오류 없이 그 transport가 호출됐다. `CustomDefaultTransportIgnoresProxy`는 실제 외부 요청 없이 이를 검증한다.

custom transport의 기존 프록시 동작을 단정할 수는 없지만, 요청한 proxy가 보장되지 않는 것은 확정이다. 적용 불가능한 transport에 명시적 네트워크 옵션이 지정되면 오류를 반환하는 편이 안전하다.

### F35 — segmented 전송의 속도 제한 미적용

[hlsStreamTo](../client/download.go#L2179)와 dashStreamTo는 RateLimitBytesPerSecond를 내부 downloader에 넘기거나 writer/reader에 적용하지 않는다. 속도 제한 1 byte/s, context 1초에서 HLS 미디어 10바이트가 성공적으로 저장됐다. `HLSIgnoresRateLimit`으로 확인했다. 일반 stdout의 streamToWriter도 같은 제한을 사용하지 않는다.

프로토콜과 출력 경로에 독립적인 제한 계층을 적용해야 한다. 병렬 작업에서는 각 worker마다 전역 제한량을 허용하지 않도록 공유 budget을 사용할 필요가 있다.

## 정적 경로에서 확인한 추가 문제

### F27 — FFmpeg 출력은 transactional하지 않음

[FFmpegMuxer.Merge/mergeArgs](../internal/muxer/ffmpeg.go#L47)는 최종 outputPath를 `-y`와 함께 직접 전달한다. 파일을 열고 난 뒤 실패·취소하면 이전 정상 출력을 보존할 경로가 없다. puremux의 임시 파일 보호도 fallback에 들어가는 순간 적용되지 않는다. `-y`의 덮어쓰기 동작은 [FFmpeg 공식 문서](https://ffmpeg.org/ffmpeg.html#Main-options)에서 확인했다. 실제 바이너리 실패 재현은 하지 않았다.

FFmpeg도 동일 디렉터리의 임시 출력에 실행하고 성공 및 검증 후 교체해야 한다. 실패 cleanup은 이번 시도에서 생성한 파일에만 적용해야 한다.

### F28 — 선택한 audio 대신 AV 입력의 audio를 자동 선택

[mergeArgs](../internal/muxer/ffmpeg.go#L78)는 `-map`을 지정하지 않는다. AV 입력과 별도 audio 입력을 병합할 때 FFmpeg의 자동 선택은 audio 채널 수, 동률이면 stream index를 기준으로 삼으므로 선택한 별도 audio를 무시할 수 있다. 이는 [FFmpeg 자동 stream 선택 문서](https://ffmpeg.org/ffmpeg.html#Automatic-stream-selection)와 현재 인자 구성에서 도출한 조건부 결과다. 실제 FFmpeg fixture 실행은 하지 않았다.

일반 병합은 `-map 0:v:0 -map 1:a:0`처럼 선택한 트랙을 명시해야 한다. 사용자 ExtraArgs와의 우선순위도 정의해야 한다.

### F29 — no-overwrites의 TOCTOU와 공유 part 이름

[shouldSkipExistingOutput](../cmd/ytv1/video_workflow.go#L241)은 Stat만 하고, 실제 Download는 그 뒤 다른 단계에서 파일을 만든다. 검사 사이에 다른 실행이 출력을 생성해도 덮어쓰기를 막지 않는다. 동시에 같은 목표를 받으면 둘 다 동일한 `<output>.part`를 쓰므로 교차 truncate/write/rename도 가능하다. 메모리 race detector가 잡는 종류가 아니다.

목표 파일의 선점을 원자적으로 수행하고, no-overwrites를 최종 설치 단계까지 전달해야 한다. part 이름을 무조건 랜덤으로 바꾸면 resume와 충돌하므로 목표별 잠금/소유권과 재개 정책을 함께 설계해야 한다.

### F30 — 오래된 handler가 새 SOOP endpoint를 만료시킬 수 있음

[serveInProcess wrapper](../internal/source/soop/agentwire.go#L243)는 old handler의 종료를 관찰한 뒤 `streams[p.BNO]`에 있는 엔트리의 expires를 현재 시각으로 바꾼다. ticker cleanup과 달리 엔트리 URL/세대가 자신과 같은지 검사하지 않는다. old handler가 완료 판정 후 락 대기 중 새 endpoint로 교체되면 새 엔트리를 만료시킬 수 있다.

생성 시의 endpoint identity 또는 generation을 캡처해 조건부 갱신해야 한다. 같은 파일의 ticker가 사용하는 URL 일치 확인을 종료 wrapper에도 적용할 수 있다.

### F31 — 취소용 deadline과 읽기용 deadline의 경쟁

[streamAgentMedia](../internal/source/soop/agentstream.go#L194)의 watcher는 취소 시 read deadline을 now로 설정하지만, loop는 ctx.Err 검사 후 다시 now+15s로 설정한다. 두 동작 사이에 취소가 오면 loop가 취소 deadline을 덮어써 readAny의 종료를 지연시킬 수 있다.

취소 시 해당 소켓을 닫거나 deadline 설정을 취소 상태와 조정해야 한다. bootstrap/session handshake도 caller context 대신 개별 timeout에 의존하므로 즉시 취소 계약과 구분할 필요가 있다.

### F32 — SOOP VOD 파일 배열 중 빈 항목을 조용히 누락

[extractVOD](../internal/source/soop/soop.go#L170)는 Files 중 URL이 비어 있거나 variants가 없으면 continue한다. 다른 part가 있으면 전체 결과를 성공으로 반환하고 해당 part의 duration도 합산하지 않아 누락이 드러나지 않는다.

API가 불완전한 part 정보를 반환할 때 full VOD인 것처럼 저장할 수 있다. 명시적 unavailable part 정보로 내보내거나 오류를 반환해야 한다. part별 다른 품질을 위치 기준으로 대체하는 matchVariant의 동작도 사용자에게 설명할 필요가 있다.

### F33 — playlist continuation 취소를 일반 경고로 소비

[GetPlaylist continuation loop](../client/playlist_transcript.go#L185)는 browse의 모든 오류를 warning으로 전환해 continue하고 마지막에 info,nil을 반환한다. caller 취소·deadline도 같아서 일부 playlist를 정상 조회한 것처럼 반환할 수 있다. F12의 item 실행 취소와는 별도의 추출 단계 문제다.

context 오류는 즉시 반환하고, 네트워크/일부 continuation 실패를 허용하는 정책과 구분해야 한다. 부분 결과를 같이 반환한다면 partial 상태를 명시해야 한다.

## 최적화·개선 제안

아래 항목은 속도 향상을 측정한 결과가 아니라, 코드에서 확인한 비용과 검증 공백에 대한 제안이다. 기존에 완료 처리한 최적화 전체를 무효화한다는 의미는 아니다.

| O04 | [challenge cache](../client/challenge_cache.go#L193)는 player별 n/sig 항목 개수 제한이 없다. TTL만으로 고처리량 사용자의 저장 개수를 제어할 수 없다. 엔트리 cap/LRU와 메모리 budget을 추가 | 입력 수에 따른 cache entries/heap |
| O05 | [loadDecipherer](../client/challenge_cache.go#L152)는 JS body 캐시 hit에도 새 Decipherer를 생성한다. 서로 다른 영상의 cold challenge가 같은 player runtime을 반복 구축할 수 있다. bounded per-player decipherer 재사용과 runtime mutex 대기를 비교 | cold/warm 추출 p50/p95, JS compile CPU |
| O06 | [HLS parseSegments](../internal/downloader/hls.go#L213)는 새 segment 필터링 전에 매 refresh마다 모든 EXT-X-KEY를 fetch한다. key URI/버전/회전 정책을 고려한 제한된 캐시 또는 lazy fetch를 검토 | manifest당 key 요청 수, 시작 지연 |
| O07 | direct HTTP/HLS/DASH/segment reader/post-live/MP3의 설정·오류 변환이 중복되어 F15/F16/F35처럼 누락된다. 옵션 전달 및 skip/rate/error 처리를 공유하고 차이가 필요한 부분만 명시 | 옵션×프로토콜×출력 방식 계약 테스트 |
| O08 | 현재 회귀 테스트는 기존 수정의 단일 조건에 강하다. 잘못된 범위+재시도+완료 이웃, cache eviction+source stream, 취소+recording, selection+postprocess처럼 교차 조건을 추가. 실제 FFmpeg 실패/선택, 긴 SOOP reconnect 및 CDN 가용 window는 별도 환경 gate로 유지 | 음성/영상/바이트/최종 경로 assertion, 오탐 없는 실패 탐지 |

## 미구현·지원 범위의 별도 정리

지원하지 않는 기능을 모두 버그라고 계산하지는 않았다. 다음은 현재 구현과 범위를 문서에 명확히 표시할 필요가 있는 부분이다.

| 기능 | 현재 상태 |
| --- | --- |
| 숫자 itag 단독 선택 | 지원하지만 selector 내부 `137+140`, `137/22`는 parser가 처리하지 못함 |
| 일반 yt-dlp selector 문법 | 일부 builtin, ext/height/width/fps만 지원; 문자열 metadata filter와 다중 audio/video mux는 일반 구현이 아님 |
| DASH SegmentList/SegmentBase index addressing | 명시적 구현 부재; 조용히 다른 경로를 타는 경우는 F18 |
| dynamic DASH 가용 window | F17; 시간 경계와 장시간 운용을 추가 구현해야 함 |
| DRM/SAMPLE-AES | 지원 대상에서 제외할 수 있으나 HLS처럼 오류/제외를 일관되게 표시해야 함; DASH는 F19 |
| source 자막/playlist | public API 내부의 ensureSession/GetPlaylist는 YouTube 전용; 다른 source 요청은 기능 미지원 대신 잘못된 YouTube 입력 오류가 날 수 있음 |
| 분리된 non-HLS OpenStream | 일반 병합 스트림 제공이 아니라 단일 포맷 fallback을 사용; StreamOptions의 선택과 실제 전달 format을 문서화할 필요 |
| 일반 파일 녹화의 graceful stop | F25; EOF와 cancel 사이의 별도 finalize 계약이 없음 |

## 유지할 부분과 판단

기존 수정의 contiguous-prefix truncate, context-aware per-key lock, Parts 복사, bounded HLS/DASH worker, puremux 임시 출력, DVR Finish/Close 분리는 유효한 개선이다. 테스트가 이런 동작을 회귀 방지하고 있다는 점도 확인했다. 위 발견은 대체로 그 경계 밖의 조합과 다른 backend에 남아 있다.

판단: **Request Changes**. 특히 F01–F04, F24–F27, F29부터 처리할 것을 권한다. public API를 깨지 않고 내부 전송 검증·출력 설치·종료 정책을 정리하는 방향이 적절하다.

감사를 완료하는 데 추가 사용자 답변은 필요하지 않았다. 구현 전에 결정할 정책은 라이브 stop 시 자동 finalize 여부, 프로세스 간 출력/아카이브 공유 보장 범위, 지원하지 않는 addressing의 오류 계약이다. 후속 작업은 구현 계획의 pending 항목에 기록했다.
