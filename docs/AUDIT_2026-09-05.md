# ytv1 전체 저장소 감사 — 2026-09-05

기능 결함·경계 조건·수명/동시성 문제 **43개(P1 22, P2 21)**, 별도 최적화·검증 개선 **8개**를 기록했다. 최초 감사에서는 구현을 수정하지 않았다. 이후 사용자 요청에 따라 F01–F43 및 O01–O08의 후속 수정을 진행했다. 현재 처리 결과와 지원 범위는 [수정 보고서](AUDIT_FIXES_2026-09-05.md)를 참조한다.

이번 결과는 로컬 소스와 fixture 기반 감사다. 현재 YouTube/SOOP 실서버, 장시간 실방송, 외부 FFmpeg 프로세스까지 검증한 결과가 아니며 모든 결함이 발견되었다는 보장은 하지 않는다. 각 항목에 재현 결과와 정적 경로 확인을 구분했다. P1은 데이터 손실·panic·핵심 다운로드/재생 실패로 먼저 수정할 항목, P2는 특정 옵션/입력/장수명 사용에서의 오작동이다.

## 검증 범위와 결과

- public client API, 다운로드/재개/병합, HLS/DASH, SOOP agent와 DVR, 메타데이터/자막/selector/archive, URL·POT·세션 캐시의 주요 경로를 확인했다.
- 기존 상태: `go test ./...`, `go vet ./...`, `go test -race ./...` 모두 통과했다.
- 추가 audit 재현 검사 21개에서 결함 동작을 확인했다. 별도 opt-in race 검사 1개도 수행했다. 검사는 Go overlay로 실행했다. 원본 production 파일과 기존 테스트 파일을 변경하지 않았다.
- 기본 테스트 통과는 아래 경계 조건에 문제가 없다는 뜻이 아니다. audit 검사는 **문제가 실제로 발생함을 assertion**하므로 PASS는 결함 재현 성공이다.
- 추가 opt-in `TestAuditPartsRace`는 공유 Parts 배열의 동시 읽기/쓰기에서 `WARNING: DATA RACE`, exit 1을 발생시켰다. 서로 다른 복사본이라고 여긴 객체의 배열 alias를 검사한 결과이며, 기본 suite가 race 실패했다는 의미는 아니다.

### F01 [P1] 실패한 청크 다운로드를 재개하면 0으로 채운 파일을 완료 처리

위치: [client/download.go:1750](../client/download.go#L1750). **재현: TestAuditSparseResumeAccepted**.

청크 경로는 파일을 전체 길이로 먼저 늘린다. 일부 청크 실패 후 .part 크기는 이미 전체 길이이며, 다음 실행은 이 크기부터 Range를 요청한다. 416 응답을 무조건 완료로 처리하여 빈 구간을 검증하지 않고 최종 파일로 rename한다. 재현에서는 실패 후 재시도한 8바이트 파일 전체가 0인데 성공했다.

수정 방향: 파일 크기와 완료된 청크를 분리해 기록하거나, 재개 가능한 연속 prefix까지만 보존한다. 416은 원격 길이·실제 완료 상태를 검증한 뒤 처리한다.

### F02 [P1] puremux 실패 시 이전의 정상 출력 파일까지 삭제

위치: [internal/muxer/puremux.go:96](../internal/muxer/puremux.go#L96). **재현: TestAuditMergeFailureDeletesExistingOutput**.

하위 remuxer는 별도 임시 파일에 쓰지만 상위 Merge 실패 경로는 outputPath를 삭제한다. 입력 파일이 존재하지 않는 경우에도 원래 있던 정상 출력이 사라졌다. installPureMuxOutput의 기존 파일 보존 설계도 상위 삭제로 무력화된다.

수정 방향: 현재 시도가 만든 임시 파일만 정리하고 기존 목적 파일은 성공적인 교체 시에만 변경한다.

<a id="f03"></a>
### F03 [P1] 같은 archive를 연 두 실행이 서로의 기록을 덮어씀

위치: [client/download_archive.go:35](../client/download_archive.go#L35). **재현: TestAuditArchiveTwoHandlesOverwrite**.

각 핸들은 열 때 EOF로 seek한 위치를 유지하며 O_APPEND가 없다. 두 핸들을 먼저 열고 A.Add, B.Add 순서로만 실행해도 B가 A의 행을 덮어쓴다. 인스턴스별 mutex는 다른 인스턴스/프로세스를 보호하지 않는다.

수정 방향: O_APPEND와 필요한 파일 잠금을 적용하고, 중복 다운로드 방지는 단순 Has/Add 사이의 별도 예약 정책으로 다룬다.

### F04 [P1] 잘못된 HLS AES IV가 라이브러리 panic 유발

위치: [internal/downloader/hls.go:324](../internal/downloader/hls.go#L324). **재현: TestAuditShortIVPanic**.

parseKey는 IV=0x01을 1바이트 IV로 받아들인다. 이후 NewCBCDecrypter가 panic한다. 짧은 정수 IV를 지원하려면 16바이트로 정규화해야 하며, 범위 밖 값과 잘못된 hex는 명시적 오류가 필요하다. 현재 잘못된 hex는 기본 IV로 조용히 대체되기도 한다.

수정 방향: 파싱 단계에서 IV 표현·길이를 검증하고 정규화하며, 복호화 직전에도 길이를 확인한다.

### F05 [P1] 잘못된 DASH duration이 인덱스 초과 panic 유발

위치: [internal/downloader/dash.go:504](../internal/downloader/dash.go#L504). **재현: TestAuditDurationPanic**.

PT1처럼 숫자로 끝나는 값을 넣으면 숫자 스캔 결과 j==len(part)인데 part[j]에 접근한다. MinimumUpdatePeriod 또는 음수 반복 확장용 duration을 통해 외부 MPD 입력이 도달할 수 있다.

수정 방향: 단위 문자가 남아 있는지 확인하고 숫자 범위와 duration overflow도 검증한다.

<a id="f06"></a>
### F06 [P1] SOOP WebSocket heartbeat가 연결 후 2초부터 쓰기 timeout

위치: [internal/source/soop/wsconn.go:41](../internal/source/soop/wsconn.go#L41). **재현: TestAuditWebSocketWriteDeadlineSurvivesHandshake**.

wsDial이 read/write 공통 deadline을 설정한다. streamAgentMedia는 이후 read deadline만 갱신한다. 운영 호출의 agentDialTimeout은 2초이므로 이후 heartbeat·pong·제어 프레임 쓰기가 timeout한다. heartbeat 오류까지 무시하여 원인 파악이 어렵다. 재현에서는 짧은 deadline으로 같은 상태를 확인했다.

수정 방향: handshake 완료 후 공통 deadline을 해제하고 각 쓰기에 별도 timeout을 적용한다. heartbeat 실패를 세션 종료/재연결에 전달한다.

<a id="f07"></a>
### F07 [P1] SOOP OpenStream.Close가 진행 중인 HTTP 요청을 취소하지 않음

위치: [client/stream_api.go:222](../client/stream_api.go#L222). **재현: TestAuditSourceCloseDoesNotCancelHTTP**.

OpenStream에서 만든 streamCtx는 source 경로에 전달되지 않는다. 다운로드는 원래 ctx로 실행되고 Close는 사용하지 않은 자식 context만 취소한다. pipe reader를 닫아도 응답 헤더나 본문 수신을 기다리는 요청은 계속 남는다. 로컬 서버가 요청 취소를 받지 않는 것을 확인했다.

수정 방향: 메타데이터에는 metaCtx, 전체 media goroutine에는 streamCtx를 넘기고 Close가 그 context를 취소하게 한다.

<a id="f08"></a>
### F08 [P2] 메타데이터 복사본의 Parts 배열 공유로 캐시 오염 및 data race

위치: [client/client.go:1212](../client/client.go#L1212). **재현: TestAuditPartsAlias / TestAuditPartsRace**.

Formats 슬라이스만 복사하고 내부 Parts는 복사하지 않는다. 반환 객체의 Parts를 수정하면 세션 캐시와 다른 복사본까지 바뀐다. 별도 복사본을 동시에 읽고 수정하는 opt-in 검사에서 race detector 경고가 발생했다. 기존 기본 race suite는 이 입력을 검사하지 않는다.

수정 방향: Formats[].Parts와 소유권을 넘기는 source MediaHeaders 등 중첩 참조를 깊게 복사한다.

<a id="f09"></a>
### F09 [P2] KeepIntermediateFiles / --keep-video가 실제 muxer에서 무시됨

위치: [internal/muxer/puremux.go:75](../internal/muxer/puremux.go#L75). **정적 경로 확인**.

client.downloadAndMerge는 keep 옵션을 검사하지만 PureMuxMuxer.Merge와 FFmpegMuxer.Merge가 성공 시 입력 두 파일을 먼저 삭제한다. client의 나중 cleanup을 생략해도 파일을 보존할 수 없다.

수정 방향: 입력 정리 책임을 client 다운로드 계층으로 통일한다. 실제 muxer를 사용한 keep 옵션 통합 검사를 추가한다.

<a id="f10"></a>
### F10 [P1] YouTube OpenFormatStream이 HLS 미디어 대신 playlist 텍스트 반환

위치: [client/stream_api.go:104](../client/stream_api.go#L104). **재현: TestAuditYouTubeHLSOpenReturnsManifest**.

두 HLS 트랙 병합의 특별 경로를 제외하면 선택한 URL을 GET해 그대로 반환한다. 단일 HLS audio/progressive 및 DASH URL을 선택하면 manifest가 나간다. 재현 결과 반환 스트림의 첫 바이트는 #EXTM3U였다. 종료된 live-adaptive의 sq 조각 처리도 이 경로에 없다.

수정 방향: Download의 프로토콜 분기를 공통 io.ReadCloser 기반 스트림 개방 계층으로 추출하여 OpenStream과 공유한다.

### F11 [P1] 비-YouTube OpenStream은 모든 포맷을 HLS로 취급

위치: [client/stream_api.go:219](../client/stream_api.go#L219). **정적 경로 확인**.

수정 방향: source 포맷의 실제 protocol에 따라 direct/HLS/DASH를 분기하고 공통 media transport를 사용한다.

64MiB를 넘는 응답은 LimitReader EOF를 정상 종료로 보아 잘린 파일을 Sync/Close하고 nil을 반환한다. 원래 파일을 바로 truncate하므로 실패 시 기존 thumbnail도 잃는다. RequestHeaders와 RequestTimeout도 이 메서드에서는 적용되지 않는다.

수정 방향: limit+1 방식으로 초과를 감지하고 임시 파일에 쓴 뒤 성공 시 교체한다. 공통 요청 설정을 적용한다.

<a id="f37"></a>
### F37 [P2] 템플릿 토큰이 들어 있는 제목에서 출력 이름이 비결정적

위치: [client/output_template.go:69](../client/output_template.go#L69). **재현: TestAuditTemplateReplacementOrder (동일 방식의 내부 renderer)**.

map 순회 순서로 ReplaceAll을 여러 번 하므로 토큰 값에 들어 있는 %(id)s 등을 다시 확장할지 실행마다 달라진다. title=%(id)s 입력은 같은 template/data에서도 서로 다른 파일 이름을 만든다. CLI 예측 이름과 실제 다운로드 이름이 달라질 수 있다.

수정 방향: 원본 template만 한 번 스캔해 치환하고 값은 다시 파싱하지 않는다. renderer 중복도 통합한다.

<a id="f38"></a>
### F38 [P2] dynamic DASH의 dedup map 초기화가 이전 조각 재다운로드 유발

위치: [internal/downloader/utils.go:36](../internal/downloader/utils.go#L36). **정적 경로 확인**.

trackSeen은 4096개를 넘으면 전체 map을 지운다. 예전 설계는 lastSeq가 방어했지만 현재 dynamic DASH는 lastSeq 검사를 의도적으로 생략한다. 다음 manifest window에 아직 있는 URL까지 잊어서 과거 조각을 다시 append하고 timestamp가 역행할 수 있다.

수정 방향: 현재 manifest window 기준으로만 seen 항목을 정리하거나 안정적인 segment identity 기반 bounded LRU를 사용한다.

<a id="f39"></a>
### F39 [P2] NoEmbedMetadata가 파일 이름에 필요한 제목·작성자까지 제거

위치: [client/download.go:501](../client/download.go#L501). **정적 경로 확인**.

downloadAndMerge가 시작하자마자 meta를 빈 구조체로 만든 뒤 meta.Title/Artist를 기본 파일명과 output template 렌더링에 사용한다. library 사용자가 metadata embedding만 끄면 제목/작성자 토큰이 unknown으로 변한다.

수정 방향: 명명용 정보는 보존하고 Muxer.Merge에 넘기는 metadata 인자만 마지막 단계에서 비운다.

<a id="f40"></a>
### F40 [P2] 멀티소스 기능이 archive와 JSON 메타데이터에 반영되지 않음

위치: [client/ytdlp_json.go:125](../client/ytdlp_json.go#L125). **정적 경로 확인**.

SOOP 결과도 extractor=youtube, webpage_url=youtube.com/watch?v=<숫자>로 직렬화한다. DownloadArchive.Add는 YouTube 11자리 ID만 허용하므로 SOOP 숫자 ID를 기록하지 못한다. source.Media.WebpageURL은 public VideoInfo 변환에서 버려진다.

수정 방향: source 이름·원래 webpage URL·source-scoped ID를 공개 메타데이터/JSON/archive까지 전달한다.

<a id="f41"></a>
### F41 [P1] Range probe가 200 본문 전체를 먼저 읽어 live에서 반환하지 못함

위치: [client/download.go:1831](../client/download.go#L1831). **정적 경로 확인**.

probeContentLengthWithRange는 상태 코드 확인 전에 본문을 끝까지 버린다. Range를 무시하는 서버의 일반 VOD는 전체를 불필요하게 한 번 더 수신하고, 끝나지 않는 live 200 응답에서는 fallback에 도달하지 못한다. probe용 200 빈 응답을 특별히 만드는 SOOP agent 외의 direct live source에 적용된다.

수정 방향: 206 여부와 Content-Range를 먼저 검사하고 probe 본문은 필요한 소량만 읽거나 즉시 닫는다.

<a id="f42"></a>
### F42 [P1] JSON/-g 출력이 서명·n·POT URL 해석 경로를 우회

위치: [client/stream_urls.go:19](../client/stream_urls.go#L19). **정적 경로 확인**.

SelectedStreamURLs는 URL이 있으면 resolver 호출을 생략한다. direct URL에도 n 변환/POT가 필요할 수 있으므로 -g 결과와 실제 Download URL이 달라진다. JSON builder도 원시 URL을 그대로 쓰며 URL 없는 cipher 포맷은 제외한다. cmd의 JSON 분기는 resolver 없이 builder를 호출하고 선택 옵션도 전달하지 않는다.

수정 방향: CLI의 URL/JSON 출력 전에 선택 포맷을 공통 resolver로 materialize한다. 순수 JSON builder는 변환 완료된 metadata만 받도록 계약을 구분한다.

<a id="f43"></a>
### F43 [P2] YouTube manifest 요청에서 공통 RequestHeaders와 파싱 오류 유실

위치: [internal/formats/dash.go:44](../internal/formats/dash.go#L44). **정적 경로 확인**.

DASH/HLS FetchManifest는 사용자 header를 받을 경로가 없고 Parse* 오류를 버린다. 인증/Referer가 필요한 manifest 요청이 실패하거나 깨진 XML·긴 HLS 줄이 빈 Formats의 성공 응답으로 보인다. client.loadManifestFormats는 성공 이벤트까지 발생시킬 수 있다.

수정 방향: headers/retry 설정을 받는 공통 manifest transport를 만들고 파싱 오류를 반환한다.

## 최적화·설계·검증 개선

### O01. GetVideo/GetFormats 중복 추출 제거

위치: [client/client.go:239](../client/client.go#L239).

GetVideo는 per-video mutex를 잡지만 기존 세션을 재확인하지 않고 항상 추출한다. 동시 10개 요청은 네트워크 작업 1회를 공유하지 않고 10회를 직렬 실행할 수 있다. refresh 의미를 유지해야 한다면 명시적 refresh 옵션과 singleflight를 분리한다.

### O02. 세션 캐시 접근 비용 제한

위치: [client/client.go:860](../client/client.go#L860).

put마다 전체 세션과 모든 URL을 write lock 안에서 검사한다. 기본 캐시 개수는 무제한이어서 장기 서비스에서 메모리 증가와 누적 삽입 비용이 커진다. expiry를 저장할 때 계산하고 TTL queue/LRU 및 기본 상한을 검토한다.

### O03. HLS 작업자 수와 pending 구조를 window 크기로 제한

위치: [internal/downloader/hls.go:384](../internal/downloader/hls.go#L384).

본문 fetch-ahead는 제한하지만 전체 playlist만큼 goroutine 두 채널과 결과 슬롯을 생성한다. 긴 VOD에서는 세그먼트 수에 비례한 고정 비용이 크다. 제한된 worker pool과 ring buffer로 대체한다.

### O04. DASH batch 전체 본문 보관 제거

위치: [internal/downloader/dash.go:188](../internal/downloader/dash.go#L188).

64개 batch의 모든 본문을 받아야 쓰기를 시작한다. 각 조각 상한 100MiB 기준으로 본문만 최대 6.25GiB이며 추가 복사 비용이 있다. 순서대로 즉시 쓰는 bounded window와 바이트 단위 예산이 필요하다.

### O05. per-key lock 대기에 context 취소 반영

위치: [client/keylock.go:29](../client/keylock.go#L29).

client/playerjs/token lock 대기는 sync.Mutex.Lock이므로 기다리는 요청의 deadline이 만료돼도 앞 요청이 끝날 때까지 반환하지 않는다. context-aware singleflight 대기를 사용하고 같은 client에 재진입하는 callback 계약을 명확히 한다.

### O06. DVR 요청당 Handler 생성·polling 제거

위치: [internal/source/soop/agenttimeshift.go:108](../internal/source/soop/agenttimeshift.go#L108).

요청마다 ServeMux를 다시 만들며 첫 segment 대기는 100ms sleep 루프로 취소를 확인하지 않는다. Handler를 한 번 만들고 ready/ended channel로 기다리면 요청 비용과 종료 지연을 줄일 수 있다.

### O07. 영상/음성 fetch 병렬화 및 시간축 정렬 검증

위치: [internal/muxer/live_hls.go:69](../internal/muxer/live_hls.go#L69).

현재 두 rendition을 순서대로 받아 요청 지연이 합산된다. sequence 일치만으로 짝지으며 매 조각마다 audio 첫 timestamp를 video 첫 timestamp로 이동한다. 다른 sequence 시작값·segment duration·실제 A/V offset을 가진 fixture를 추가하고 시간 기반 정렬을 검증해야 한다. 이번 감사에서는 A/V 어긋남을 실재생으로 측정하지 않았다.

### O08. 지원 계약·문서·검증 행렬 정리

위치: [client/config.go:105](../client/config.go#L105).

Config.Muxer의 nil 설명은 fallback이라고 하나 구현은 ErrMuxerUnavailable을 반환한다. 계획 Current Gap Theme에는 이미 완료된 초기 제한 설명도 남아 있다. API × source × protocol × output(file/stdout/MP3) × cancellation/resume 행렬로 실제 지원과 테스트 누락을 관리한다.
